# Engineering Guidelines & Agent Operating System (AGENTS.md)

## 1. Repository Structure & Layout

The Rysoo CV Optimization Platform is organized as a single monorepository with clearly delineated, independently testable components:

```
rysoo/
  apps/
    api/                          # Spring Boot REST API (Port 8080)
    worker/                       # Spring Boot background worker (queue consumer)
    web/                          # React + TypeScript + Vite web frontend
    mobile/                       # React Native + Expo mobile application
  services/
    cv-domain/                    # Pure domain models, value objects, ports
    cv-application/               # Application services, use cases, AI orchestration
    cv-infrastructure/            # Spring Data JPA, Supabase client/storage, Flyway
    cv-document-processing/       # Apache Tika, PDFBox, POI document ingestion & OCR
  packages/
    contracts/                    # Shared TypeScript interfaces & DTO schemas
    api-client/                   # Generated TypeScript API client (OpenAPI)
    validation/                   # Shared validation logic & rules
  infrastructure/
    render/                       # Render Blueprint & service deployment configs
    docker/                       # Dockerfile & container runtime definitions
    scripts/                      # CI/CD & developer automation scripts
  supabase/
    migrations/                   # Version-controlled Flyway & Supabase SQL migrations
    config.toml                   # Local Supabase development configuration
  tests/
    fixtures/                     # Synthetic test fixtures (DOCX, PDF, JD, malformed)
    integration/                  # Cross-service integration tests
    e2e/                          # Playwright web E2E tests
  docs/                           # Architecture, API, security, and operations docs
  .agents/                        # ECC-managed skills, rules, and workflows
  .github/workflows/              # GitHub Actions CI/CD workflows
  pom.xml                         # Root Maven parent POM (multi-module)
  package.json                    # Root npm workspace configuration
  Dockerfile                      # Multi-stage Docker build for API & worker
  render.yaml                     # Render Infrastructure Blueprint
```

## 2. Mandatory Architecture Boundaries: Option A

- **Spring Boot is the exclusive data access layer.**
- Web and mobile clients **must never** directly query, insert, update, or delete application tables through the Supabase client or PostgREST.
- Clients authenticate with Supabase Auth to obtain a JWT.
- Clients send the Bearer JWT to Spring Boot.
- Spring Boot validates the JWT (signature, issuer, expiration, audience, user claims), checks resource ownership on every query and mutation, and enforces business logic.
- Private document buckets in Supabase Storage are accessed only via Spring Boot or short-lived, ownership-verified signed URLs generated by Spring Boot.
- Never expose service-role keys, database passwords, or AI API keys to client bundles or browser consoles.

## 3. Build & Test Commands

### Java / Spring Boot Backend
- Clean & compile: `mvn clean compile`
- Run all tests: `mvn clean test`
- Run integration tests with Testcontainers: `mvn verify -Pintegration-tests`
- Package Docker image: `docker build -t rysoo-backend:latest .`

### Web Frontend (React + Vite)
- Install dependencies: `npm install`
- Run dev server: `npm run dev --workspace=apps/web`
- Run typecheck: `npm run typecheck --workspace=apps/web`
- Run unit tests: `npm run test --workspace=apps/web`
- Run E2E tests: `npm run test:e2e --workspace=apps/web`
- Build production bundle: `npm run build --workspace=apps/web`

### Mobile App (React Native + Expo)
- Run typecheck: `npm run typecheck --workspace=apps/mobile`
- Run unit tests: `npm run test --workspace=apps/mobile`

## 4. Coding Conventions & Standards

- **TypeScript**: Strict mode enabled (`"strict": true`). No unchecked `any`. Explicit return types on exported functions.
- **Java**: Java 21 LTS baseline. Strong encapsulation, immutable value objects where possible, no Lombok magic that obscures constructors, `@Valid` bean validation on all controller inputs.
- **Clean Architecture**: Domain entities in `services/cv-domain` must remain completely decoupled from Spring frameworks, database annotations, and external AI SDKs.
- **Styling**: Modern, premium CSS design system, responsive layouts, dark/light harmonious color tokens, accessible contrast, and zero layout shift. Root brand assets (`logo.png`, `logo.svg`, `favicon.ico`) must be prominently integrated.

## 5. Security & Factual Integrity Rules

- **Zero Hallucination / Fabrication**: The AI engine must **never** invent employment dates, employers, qualifications, certifications, metrics, or degrees. All generated optimization claims must be grounded in verified source CV evidence.
- **Distinguish Qualification Confidence**:
  - `DEMONSTRATED`: Explicitly documented with evidence.
  - `PARTIALLY_SUPPORTED`: Transferable or partial match requiring user confirmation.
  - `MISSING`: Not found in the CV; never fabricated.
- **Explainable Match Assessment**: Any match metric must provide clear reasons and must never promise recruitment or ATS guarantees.
- **Injection Defense**: All extracted document content and job descriptions must be sanitized and treated as untrusted data before prompt assembly.

---

## 6. Pre-Commit Validation & Gate Requirements

Before committing or claiming phase completion:
1. All relevant unit and integration tests must pass locally.
2. Code must compile without warnings or lint errors.
3. Database migrations must be forward-only and tested against empty schemas.
4. `docs/progress.md` must be updated with commands run, test outputs, and gate decisions.

---

## 7. Strict Anti-Fabrication & Deployment Integrity Rules

- **Never report an unexecuted test as passing.**
- **Never claim a tool, library, or deployment is configured or verified unless checked via live commands.**
- **Never invent credentials, URLs, repository links, or test outputs.**
- **Never bypass failing tests by commenting them out or disabling assertions.**
